The assistant should belong to the user.

SPAI’s long-term direction is simple: make personal AI feel owned, safe, extensible, and permanent.

  • No hidden ad model. SPAI is not planned as an ad platform. The product should make money from the product, not from user attention, tracking, or behavioural profiling.
  • Minimal data by design. SPAI’s account direction is to ask only for what is genuinely needed: an email address, optional GitHub linking for repository access, purchase/receipt records where required, and a user-controlled recovery setup.
  • GDPR-minded from the start. SPAI is being designed around legitimate-interest minimalism, privacy by default, and avoiding unnecessary personal data collection such as real names or phone numbers.
  • User-controlled recovery. The direction is to use a unique code and a custom passphrase set by the user for data security and recovery, without keeping unnecessary personal details on file.
  • No forced cloud memory. Your files, chats, and memories should not have to live behind someone else’s platform.
  • No hidden tool access. Apps, files, and automation should be permission-gated and visible to the user.
  • No one-size-fits-all model. SPAI is being designed to support different local models, backends, and hardware profiles.
  • No subscription trap for the core product. The goal is that once you own SPAI, you keep the version you bought.

No ads. No personal data business model.

SPAI is being built around the idea that personal AI should not require personal-data harvesting. The product should be paid for as a product, not funded by tracking the user.

  • No personal data tracking, selling, or redistribution. SPAI is not being designed around behavioural advertising or reselling user information.
  • Minimal information required. The planned account model does not require a real name, phone number, or unnecessary personal details.
  • Email-first account access. SPAI may ask for an email address, and users may optionally link GitHub for repository/source access after purchase.
  • Receipts only where needed. Purchase records, receipts, and access records may be kept where necessary for ownership, support, and legal/accounting reasons.
  • Recovery without over-collection. Users are planned to receive a unique code and set their own custom passphrase for data security and recovery.
  • GDPR-minded approach. SPAI is being built to follow privacy-by-default principles and collect only what is genuinely needed for legitimate product operation.

Open where it matters. Owned where it counts.

SPAI’s direction is to make ownership practical: users should be able to inspect what they buy, builders should be able to improve the ecosystem, and useful work should be rewarded.

  • Repository access with purchases. The direction is that purchases grant access to the relevant source repository, so users can inspect the code they paid for.
  • Open-source foundation. SPAI is planned to rely on and support open-source models, backends, and tooling rather than pretending everything must be closed.
  • Builder monetisation. Useful plugins and tools should be able to earn money, while still keeping the core SPAI experience affordable.
  • Community competitions. SPAI may hold competitions and incentives to encourage better plugins, smarter workflows, and meaningful improvements.
Environmental direction

A more responsible alternative to endless cloud AI dependency.

SPAI is not claiming every local setup is automatically greener than every cloud setup. The point is different: massive AI data centres, constant remote inference, duplicated infrastructure, cooling, networking, and hardware build-out are often treated as invisible costs. SPAI’s local-first direction gives users a way to reuse hardware they already own, reduce unnecessary cloud dependence, and make AI feel less like another always-renting data-centre product.
